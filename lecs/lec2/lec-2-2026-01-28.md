What is distributed shared memory?
From TLB (page table):
1) local memory (DRAM)
2) local disk (SSD/HDD)
*New 3) Remote machine memory
Problems;
- synchronisation/consistency is going to be horrible.
  Local copy cache movement from the DRAM etc to remote machine memory will have problems.
  caching issues.
- Fault tolerance is low. If that memory is down, there is going to be a hole in the memory for
  that.
- Heterogenuous archs, how do you handle mismatches in the number of bits in your address space.
- Does not distribute computation, only distributes data.

Addressing ony byte from the memory would prove too expensive if distributed shared memory is used.

int bar(int *ptr)
What does the original RPC spec do?
Don't do this. The memory that the pointer is pointing to is not accessible to the server. Therefore
do not do this.
Options for this?
- Copy on caller, send value(*ptr) to server, server has the value now.
Problems?
- Huge amount of data -- perf problems.
- linked-list/heap deep structures -- how much do we copy and send?
- synchronization problems. The remote entity (server) might make changes which is not directly
  reflected onto the (client) local copy.

Transport Layer
Goals?
- High perf, fast response time. => no handshaking
- Not bulk transfers.
- low load on server i.e the servers need to be highly scalable.
- Not much state per client => memory problems.

Assumptions?
- No large messages
- Local area (assume that the RPCs are going to travel less distance).

---

Semantics of the RPC calls:

1) Local machine - exactly once
2) At-least-once semantics => Multple time, 1 or more(not RPCs)!
When ok?
- Idempotent ops => Same result even when executed multiple times.
Eg:
- read()
- pwrite() with a position specified => write in the same place again and again.
=> Not Idempotent => add(), subtract(), append() etc
Why not okay for RPC? 
- RPCs need to support all procedures (and not just idempotent ones).
3) RPCs => At-most-once semancits
- Guarantees exactly once when there are no errors.
- If there is an error, it could be 0 or 1 time.

---

At-most-once semanticsl

General idea:
- detect duplicate calls.
- discard dups
- if a request that was seen before, return the previous results. If a client is sending the same
  request again and again, return the result that was computed once.
Implications:
- 1 outstanding RPC => assumed in the paper.
How many responses must server remember?
- Just the last one to compare with the new one due to the 1 outstanding RPC assumption.

---

At-most-once acks

How can client know server received call?
Naive => ACK - extra communication though.
Optimization => Result serves as ACK (assuming that the RPC is relatively short living). Reduces
the load on server and network.
How can server know client received call?
Naive => ACK
Optimization => The next call packet from that particular client serves as the ack. This works fine
as long as there is only 1 outstanding request and the service is synchronous.
There are some fallbacks (send an ACK if there is no next call packet).

Call-id/Seq num:

Why call-id in result?
- matching?
- old/discarded/duplicated packets need to be dropped.
- client uses this 
Why in call packet?
- call-id for the last executed request => i.e the last request was executed successfully.
=> i > L (i = L+1 usually) => old once was received.
=> i = L (old message, was retried, return the previous result)
=> i < L (discard it) => the call id received is old so it's an old request.
L => Last sequence.

What happens on failures?
Server crash: 
- Lost the export table + call table
- Reboot => new service id => Breaks binding with client
- Client informed on next interaction since the service id doesn't match
- If re-send, what happens to last RPC before crash? 
    - Maybe exec, maybe not -> Notify client?
    - At-most-once (not "Exactly once")
    - At this point it is not know if the server executed the RPC call or not.
    - Therefore, send a return code signifying failure.
    - Client decides what needs to be done to cean things up.

Client crash:
- Ongoing RPCs
    - Server is going to continue doing that work, it's wasted work, client is not going to take
      this value.
    - Reboot, what is the next seq number? => based on time, so that we know it's a new req on the
      server. Therefore the server does not need to keep track of anything that client says except
      for the last sequence number that it sent.
    - Is it a new client from the server side after crash?
        - Maybe/Maybe not, depends on the implementation. The RPC layer tracks the machine ID and
          the PID.
    - How does the server respond?
